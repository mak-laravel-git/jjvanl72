# Dentist case persistence

Dentists persist cases from create-case (draft and submit). Clients are admin-managed (`dental_clients`). Submitters pick any active client on the case; one client can have many cases. Ownership is `created_by`. Patients are created on first save (`patients.patient_number`).

## Pricing

Package prices come from admin CRUD (`dental_package_prices`): one fee per **product + material + service (+ output for Manufacture)** — not additive Design approval + Print + Models lines. The manufacturing method is implied by the material ("Milled …" / "… Printed") and models are covered by Output, so **Manufacturing Method and Model Service are no longer dentist or admin choices**; the legacy `manufacture_method` / `model_service` columns are always written `null` and ignored when matching. `PackagePriceResolver` (PHP) and `resolvePackagePrice` (JS) must stay in sync; `catalogRows()` de-duplicates per key with the same ordering as the lookup (current rows first, then legacy rows preferring `none`/`mill`, then lowest id) so UI and server always agree. Migration `2026_11_16_090000_collapse_manufacture_package_prices_to_output_key` collapses legacy 12-combo rows to one per output, archiving every changed/removed row in `dental_package_prices_archive` (`down()` restores them). Case list/detail `manufacturing_type` is derived from the item materials (legacy stored value as fallback). Shade and parameter `config` never affect price. Design/approve packages ignore output. Defaults resolve server-side when `price_overridden` is false; dentists may override per item (`unit_price` + `priceOverridden` in item config). Persist real `dental_case_items.unit_price_minor`. Totals = sum of effective unit × quantity; tooth-kind rows fully covered by a bridge line are skipped to avoid double billing (create-case `calculateTotals`, checkout summary, Prescription.pdf total, and ShowCase `cart_total` / `line_total`). Bridge `quantity` is forced server-side to span tooth count. Catalog exposes `packagePrices[]`. On save with items, a single-page stacked **Prescription.pdf** is generated (jspdf) and stored as a case file (`requirement_code_snapshot=prescription`) so it travels with the case zip; PDF generation failure aborts the save. Prescription.pdf layout: top brand logo/stub + title; left column case info + service once; right column causes/items with prices; bottom total bar. Service is not repeated per item.

## Medium / tablet layout (≤1440px)

Left/right create-case panels are **overlay drawers** (absolute left/right, over the full-width chart — not inline columns). Both start open; each closes only via its × (center/chart clicks do not close them). Edge toggles re-open a closed panel. Selecting a tooth (catalog/material/edit) re-opens both panels. Navigating to another create-case function keeps existing open/close behavior. On config/material screens, the center materials pane insets into the open gap between drawers so cards stay visible/clickable; large desktops (≥1441px) keep the normal 3-column grid. Medium UI type is slightly smaller than large (product buttons, option/parameter grids, material cards, Clear/OK); tooth chart geometry/labels stay unchanged.

## Chart

Tooth chart idle state is black-and-white (white fill, black stroke/labels); color only after selection/prescription. Labels use a professional UI sans (`Segoe UI` / system-ui) and Palmer 1–8; FDI remains in data/state. Occlusal shapes live in `toothChartGeometry.ts` (incisor/canine/premolar/molar + molar grooves) aligned to Tooth Chart.jpg. **Bridge rule** (single source: `bridgeMembersQualify` in `helpers.ts`, mirrored server-side by `ValidatesDentalCasePayload::validateBridgeItems` on submit): a bridge needs ≥1 retainer (`crown`/`implantCrown`) **and** ≥1 explicitly prescribed `pontic` in its span — two crowns, two pontics, or a gap auto-filled without a pontic Rx are not a bridge. It gates auto-join, the consecutive-save path, the green mid-dots (shown only inside qualifying runs), "Join as bridge", and `confirmBridgeGroups` (groups without retainer+pontic are not saved as bridges). The bridge line is always configured/billed from a retainer, never a pontic. Its description (Rx panel, review modal, ShowCase, Prescription.pdf) comes from `bridgeAbutmentTeeth`/`bridgePonticTeeth` fed with the case's lines: abutments = span teeth carrying a crown/implant-crown line, everything else in the span (explicit pontics + auto-filled gap teeth) is listed as pontics; legacy bridges with no retainer line fall back to the span ends — so a crown inside a span is never labelled a pontic. Bridge auto-start after two consecutive single-tooth saves requires the same arch (`teethRangeBetween`); bridge toasts/banners use Palmer display while `bridgeFrom`/`bridgeTo`/edge keys stay FDI. Green connector lines/dots are drawn **only in bridge mode** (`showConnectors = forceConnectors`) plus the qualifying "join" dots and saved bridges — never for an ordinary multi-selection. **Copy-last gesture:** after a per-tooth item is saved (`isReplicableItem`: `mode==='teeth'`, not bridge/arch/partial) it becomes the template (`replicaTemplate`); with no template this session (e.g. a loaded case) the case's last copyable line is used (`copySource`); while idle on the project chart (nothing selected), **Ctrl/Cmd+click** copies it onto the clicked tooth and **Shift+click** copies it across the same-arch range from the last clicked/prescribed tooth (`replicateItemOntoTeeth`: skips teeth already carrying that product and bridge-covered teeth, copies material/config/price override, shade follows the current default unless customised, then re-runs the bridge rule). With a selection in progress or no template, Ctrl/Cmd toggles a tooth and Shift adds a range to the selection; Multi-select ON still toggles. Deleting the template line drops it (the next copyable last line takes over). Known limit: only single-tooth lines can join a bridge (a multi-tooth line would be billed twice where it overlaps a bridge). On Mac use Cmd (Ctrl+click is the context menu). Chart **Default shade** sets `draft.shade` for new items only; each Rx line has an editable per-item shade (`shadeOverridden` when changed in the Rx panel; Apply default shade to all clears overrides). On Save bridge, the first abutment shade applies to the bridge line and to span tooth rows that are not shade-overridden. Shade never affects package price.

## Digital file slots

Digital Files starts with three fixed fields: Upper Arch, Lower Arch, Bite Scan (`upperArch`, `lowerArch`, `biteScan`). Dentists may add more fields. Empty fields persist as `dental_case_file_slots` (requested files). Real blobs stay in `dental_case_files` keyed by `requirement_code_snapshot`. After save (non-draft), **Lab** (portal role) and **assigned Designers** may upload into empty slots and add their own slots via `cases.file-slots.*` (`manageFiles` policy). Owners manage slots through create-case save (`file_slots` JSON + `files`).

## Other

Foreign cases return 404. **Load** on ShowCase opens create-case for the same record (`cases.edit` via `caseDetail.database_id`) for any status — drafts and submitted are both editable in place; saving updates the same row. `intent=draft` does not change status on submitted cases; `intent=submit` sets submitted. Case show maps stored prescription items, including `kind: bridge`, span teeth, and broken edges — do not flatten bridges into one row per tooth. Bridge abutments keep their `kind: tooth` product/material prescriptions; pontics inside the span are connection-only (green chart fill + connectors, no individual material/product Rx). Case file download is `GET cases/{case}/files/download` (zip) for the owning dentist; ShowCase wires it via Wayfinder `@/routes/cases/files` `download.url(caseNumber)`. Lab can open non-draft cases they do not own for file fulfillment.
